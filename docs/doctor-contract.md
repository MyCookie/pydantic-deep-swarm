## Question

Specify `agent-team doctor` output and exit semantics for a stopped standalone clone, a running healthy runtime, an occupied lease, endpoint/model failures, and explicitly requested `--with-pi` or `--supervisor=s6` checks. Decide how the existing `bootstrap` command and any report schema remain compatible, while Pi and s6 stay optional for core validation.

# Standalone and optional doctor contract

Decision specification for issue #6, under planning map #1. This describes the subsequent build and its acceptance gate, not implemented CLI behavior. It incorporates configuration authority #2, the accepted knowledge migration contract #3, foreground serve #4, and model selection #5. No runtime implementation is needed to close this decision issue.

## Invocation and scope

`agent-team doctor` is a new diagnostic command. It accepts canonical `--config`, `--state-dir`, and `--workspace-dir` selection from #2, `--repo-root`, `--expected-revision`, `--json`, `--report`, `--timeout`, `--ready-url`, `--with-pi`, and `--supervisor=none|s6` (default none). Optional adapter inputs are `--pi-binary`, `--service-dir`, and `--s6-svstat`. Adapter-specific inputs without their scope selector are usage errors; unknown supervisors are usage errors. Pi and s6 selectors compose independently; neither is discovered, required, nor invoked by default. Explicit optional inputs resolve against invocation cwd and are reported as absolute paths. Explicit binaries take precedence over PATH lookup; absent explicit binary permits bounded PATH lookup within the requested adapter only. Ready URL defaults to #4 host/port selection; legacy `/health` suffix normalizes to `/ready`, never substitutes liveness for readiness.

Core required checks cover repository/source layout and current/expected revision when selected, Python/dependency availability, effective configuration, resolved external state/workspace path safety and observable access, active-role model discovery/selection, and enabled knowledge inspection. Runtime lease observation is informational; enabled knowledge makes its safe inspection guard required. Missing/unusable lease evidence when knowledge is disabled is a warning, not required unverified. Repository Git revision/layout are required, an expected revision mismatch fails, and dirty checkout is a warning rather than an implicit clean-tree deployment gate. Path checks do not prove future writes will succeed and never use write probes. Existing inaccessible or observably unwritable required directories fail; absent directories are reported as needing initialization when their existing safe parent has appropriate observable access. Unsupported permission inspection is unverified. Knowledge-enabled missing lock still prevents complete success, as below. A missing explicitly named config fails; unnamed absent canonical config uses and reports environment/default fallback. Source/config/path authority follows #2 exactly, including escape rejection and YAML precedence. State and workspace are validated separately.

Model checks use #4/#5 effective principal, manager, worker, plus curator only when all three memory/shared-knowledge/curator switches are enabled. Resolve inheritance exactly as those contracts specify. GET `/models` once per distinct effective endpoint, comparing endpoints by trailing-slash normalization only. Neither LLM_API_KEY nor AGENT_TEAM_API_TOKEN is sent to discovery. Successful JSON requires an object with list `data`, every ID nonempty string, no reserved `auto`; deduplicate exact IDs. Auto requires exactly one distinct ID. Explicit selections must occur exactly and may differ intentionally across roles/endpoints. Report configured and resolved values separately; do not persist auto or execute inference. Transport, HTTP/auth, malformed catalog, missing explicit ID, and ambiguous/empty auto are required failures with #4's stable model reasons. Current advertised availability is not successful inference or a live runtime configuration claim.

## Nonmutation and ownership

Doctor never installs, starts/stops/restarts, reconciles, creates runtime directories, rewrites config, acquires RuntimeLease ownership, modifies owner metadata, initializes stores, applies retention, repairs/migrates knowledge, connects SQLite to source databases, checkpoints, or creates source sidecars. Metadata reads and bounded read-only HTTP/subprocess probes are allowed. Credential-shaped child environment values are scrubbed. No ownership tokens, secrets, URL userinfo/query/fragment, raw endpoint bodies, record payloads, or unsanitized exceptions appear in any output.

Issue #3 governs knowledge inspection verbatim: use a nonmutating guard on an existing usable lock and coherent complete bundles copied into private temporary storage outside the state directory. Recover/validate only private copies, with quiesced writers and identity/coherence checks. Preserve original journals/sidecars. Private temporary material has restrictive permissions and is cleaned up. No source SQLite or immutable-mode bypass is permitted. Busy lock yields inspection_deferred; missing/unusable lock, unsupported safe locking, or unavailable coherent copy yields inspection_unavailable. Neither proves corruption or health. Owner metadata is advisory; stale metadata cannot override an OS lock. Free guarded lease means the selected state has no participating owner at observation time, not that every host process is stopped. No lock removal/replacement is remediation.

Knowledge requiredness depends on enabled shared knowledge. canonical passes. Guarded needs_initialization, migration_needed, and valid recovery_pending are compatible with startup and pass with explicit pending-action warnings: startup still performs initialization/migration/resume and may fail. #3 definite blockers (ambiguous, invalid, unsupported_schema, unsafe_path, orphan_sidecar, recovery_required) fail when enabled. Deferred/unavailable are unverified when enabled. Disabled knowledge is not inspected by default, reports disabled, and excludes it from required scope; separately observed disabled-store findings cannot become core blockers. Audit warnings with valid live canonical remain warnings.

## Runtime and optional observations

Core success does not require a running runtime. A free guarded lease and a stopped readiness endpoint are normal for a stopped standalone clone. HTTP readiness is observation-only in core scope; endpoint failure must not override a validated stopped clone. A busy lease reports occupied and warns a second serve would fail runtime_in_use, but does not prove incumbent health. Knowledge is deferred and aggregate is unverified when enabled, even with a ready endpoint. Runtime observation fields distinguish lease status, readiness endpoint result, and selected-runtime correlation. Existing `/ready` has no instance/state identity; an HTTP 200 ready body cannot prove it owns the selected state. Keep correlation unknown and never synthesize selected_runtime_ready or replace deferred SQL with HTTP health. An unrelated endpoint cannot turn an unverified clone green. `/health` is liveness only; readiness is not ongoing model connectivity per #4. API-token authentication belongs only to Agent Team probes.

`--with-pi` requires an installed executable, a successful bounded `--version` probe, and validation of the source Pi package/manifest using its existing asset/hash rules. Doctor adds the following explicit version gate; it does not claim an existing comparator policy. Trim outer whitespace from stdout, then require exactly one line containing a strict SemVer 2.0.0 version, either bare or prefixed by exactly `pi `. No `v` prefix, extra prose, multiline output, or stderr fallback is accepted. Parse numeric major/minor/patch as integers; core numbers and numeric prerelease identifiers forbid leading zeros. Compare core triples lexicographically, then SemVer prerelease precedence: release exceeds prerelease, numeric identifiers compare numerically and precede nonnumeric identifiers, nonnumeric identifiers compare case-sensitively in ASCII order, and a shorter equal-prefix identifier sequence precedes a longer one. Build metadata does not affect precedence.

Without trimming or coercing source fields, strictly parse the manifest top-level `minimum_pi_version` and every listed asset minimum, including optional, metadata, and test assets; malformed minima fail `pi_assets_invalid` even if the legacy validator accepts their syntax. The effective floor is the maximum of all those minima, and the installed version must be at least that floor. The package release `version` is not a runtime floor. Evidence includes normalized installed version, effective floor, and the package/asset paths supplying minima, without raw child output. All future valid majors meeting the floor pass because the source declares no upper bound; this means declared-minimum compatibility only, not proven API compatibility. Missing/nonexecutable binary fails `pi_binary_unavailable`; nonzero exit, execution error, or per-probe timeout fails `pi_version_probe_failed`; successful empty/unparseable output fails `pi_version_invalid`; a lower version fails `pi_version_unsupported`; invalid source assets fail `pi_assets_invalid`. These are required failures/exit1 whenever Pi is selected. It never installs, loads, approves, or reconciles assets. Installed-resource drift, when safely observed, is informational and clearly separate; this flag validates prerequisites/assets rather than asserting installation activation or session functionality. Pi status must not mutate settings/state. Legacy bootstrap and reconciler version parsing remain unchanged.

`--supervisor=s6` requires a supplied/resolved service directory and s6-svstat executable, a successful bounded status probe reporting service up, and a successful HTTP 200 `{status:ok,ready:true}` result from the supplied readiness URL. Missing tools/path, service down, auth denial, negative/malformed response, or endpoint failure fails this selected adapter gate. It reports service liveness and supplied-endpoint readiness; selected-runtime identity remains unknown, not silently asserted. No runfile is model authority, and no service command starts or restarts anything. Enabling s6 does not enable Pi. Even passing s6 checks cannot waive an unverified enabled-knowledge check. With knowledge disabled, all selected adapter/core checks may pass and exit0 without claiming selected-runtime identity.

## Aggregation, exits, and examples

Each check has status passed, warning, failed, unverified, or not_selected; explicit scope selection makes its checks required. Warnings do not imply missing verification, and no required unknown can be represented merely as a warning. Disabled/not-selected checks are nonrequired. Required failed takes precedence over required unverified, which takes precedence over passed/warnings.

- Exit0 / outcome validated: all required checks verified compatible with their declared scope; warnings and known startup actions permitted. This is not an inference, activation, or permanent-health guarantee.
- Exit1 / outcome blocked: at least one required definite validation/probe failure, or unexpected diagnostic execution/report-write failure. Report all safely obtainable independent findings.
- Exit2 / outcome unverified: no definite required failure, but at least one required check could not be completed safely. CLI parsing/usage errors also exit2, distinguished as usage_error rather than a diagnostic result.

Config contents/missing named file/path/model errors are diagnostic failures1 with structured output, not parser usage errors. Parser failures may use Click stderr without a report promise. Internal diagnostic errors use execution_error and exit1, never corrupt or validated.

| Scenario, other required checks pass | Required finding | Exit |
| --- | --- | --- |
| Stopped standalone, usable existing free lock, canonical knowledge | stopped observation; canonical passed | 0 |
| Stopped guarded state with no database/evidence | needs_initialization passed with warning | 0 |
| Fresh clone/state without usable existing lock, knowledge enabled | inspection_unavailable; absence qualified metadata only | 2 |
| Running apparently healthy runtime with occupied lease, knowledge enabled | endpoint_ready true; correlation unknown; inspection_deferred | 2 |
| Occupied lease with unavailable endpoint, knowledge enabled | incumbent health unknown; inspection_deferred | 2 |
| Knowledge disabled, healthy core checks, occupied lease | knowledge disabled; second-start warning, endpoint observation only | 0 |
| Endpoint outage, missing explicit model, zero/multiple auto, malformed catalog | required model failure | 1 |
| Missing Pi/s6 with neither flag selected | not_selected | 0 subject to core |
| Explicit Pi missing or invalid | required Pi failure | 1 |
| Explicit s6 down or supplied readiness fails | required adapter failure | 1 |
| Explicit s6 up/ready; knowledge enabled/busy | adapter passed; knowledge unverified | 2 |
| Required failure plus unavailable inspection | failure wins; preserve both findings | 1 |

One total monotonic deadline defaults to 30 seconds, with positive finite `--timeout`; all probes, copies, retries, and output preparation fit remaining budget. #3's knowledge limit remains at most 30 seconds and composes with a shorter outer budget. A per-request model/adapter timeout is a failed probe1. Deadline exhaustion preventing remaining required checks yields unverified2 unless failure1 already exists. Knowledge copy/inspection timeout is inspection_unavailable2. Probes already completed remain observations with timestamps; no snapshot-of-all-world guarantee. Cancellation cleans private material and must not leave diagnostic workers touching runtime state.

## Reports and compatibility

Text includes outcome/exit, selected config/source, final state/workspace paths, selected optional scopes, per-check status/reason/sanitized detail/remediation, lease observation, and readiness evidence with correlation caveat. JSON is one complete object on stdout with diagnostics on stderr, also for diagnostic failures/unverified; text prose is not a parsing interface.

DoctorReport schema is a new explicitly named report kind `agent-team.doctor`, schema_version1. Fields: report_kind, schema_version, generated_at, repository_root, revision/expected_revision nullable, config_file nullable and config_source, state_dir/workspace_dir nullable when resolution failed, selected_scopes, outcome, exit_code, validation_complete, checks, runtime_observation. Each check contains stable id, scope, required, status, reason, safe detail, remediation, observed_at and structured safe evidence. Null means unknown/unresolved; empty values do not substitute unknown. Runtime observation contains lease_status free|occupied|unavailable, safe owner PID/start-time when available, readiness_url, endpoint_ready true|false|null, readiness_reason and selected_runtime_correlation unknown (future additional values require explicit schema design). Model evidence includes roles, safe endpoint, configured selection, resolved ID nullable, advertised IDs; knowledge evidence includes candidate paths, #3 result, phase/archive/journal path and remediation without records. validation_complete means no required unverified check; outcome determines whether completed checks passed. Explicit not_selected entries for Pi/s6 ensure machine consumers can distinguish omission from missing prerequisites. Consumers verify report kind/version and tolerate unknown check IDs; incompatible field/status/meaning changes require a new version, not a silent BootstrapReport change.

`--report` explicitly authorizes an atomic report-only write to an operator destination outside checkout and state/workspace trees, with existing parent directory, rejecting symlinked target/ancestors and collisions with inspected inputs. Doctor creates no report parents. Private temp plus explicit report output are the only filesystem-write exceptions. Failed output write reports report_write_failed on stderr and exit1; JSON stdout includes final outcome/exit1 when serialization remains possible. Existing report is preserved on pre-replace failure; post-replace durability failure discloses uncertain persistence rather than rollback.

Existing `bootstrap` remains the legacy Pi+s6 deployed-installation gate, with its current required --pi-binary, readiness/service checks, argument aliases, existing field shape (no report_kind is added), BootstrapReport schema_version1, passed|failed|skipped check statuses, and current exit0 ready/exit1 not ready or BootstrapError/exit2 parser usage. Existing bootstrap report destinations, including external state-directory reports, remain compatible; doctor’s stricter destination rule does not change bootstrap. Its documented directory/write probes remain legacy behavior; it is not renamed to doctor and not claimed nonmutating. No doctor fields/statuses enter its extra-forbid schema, and no lossy doctor projection supplies its ready field. New doctor does not relax bootstrap's optional-deployment requirements. Shared read-only helpers may later be reused only without changing either command contract. Issue #2's future canonical configuration and #3's prohibition on bootstrap database creation/migration still apply; preservation of bootstrap report compatibility does not authorize the old conflicting config-selection behavior. Future incompatible bootstrap schema work must be explicit/versioned separately. Current tests prove baseline behavior only.

## Future acceptance gate

Implementation must demonstrate CLI text/JSON exits across the scenario table; identical aggregation for stdout/file report; parser versus config errors; scoped optional flags and independent Pi/s6 selection; Pi numeric ordering (0.9.0 below 1.0.0), prerelease ordering (1.0.0-alpha.2 below alpha.10 below release), build-metadata equality, higher optional-asset minima, future-major declared-floor acceptance, leading-zero/malformed source minima, successful empty/multiline/extra-prose probe output, failed probes and stderr-only versions; stopped versus busy lease in real processes; fresh no-lock state; stale metadata; unrelated ready HTTP server; ready runtime model outage; all #4/#5 catalog/inheritance/credential cases; every #3 knowledge result and coherent WAL/hot-journal/private-copy inspection; disabled-knowledge isolation; permission/unsafe-path failures; total/per-probe timeout precedence and cleanup; external report atomic failures and redaction. Compare source/state/workspace files, hashes, sidecars, owner metadata and locks before/after successful and failing diagnostics, apart from allowed report/private temp. A diagnostic does not prove future runtime migration or write success; separate serve and smoke acceptance remains #4/#8.

No doctor command currently exists. Implementing this future contract will require CLI/report/inspection work in the subsequent build. This decision issue can close with the reviewed specification without doing that implementation.
