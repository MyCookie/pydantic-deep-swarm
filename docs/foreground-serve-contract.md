# Foreground serve contract

This is the accepted decision contract for [issue #4](https://github.com/MyCookie/pydantic-deep-swarm/issues/4), within the [standalone planning map](https://github.com/MyCookie/pydantic-deep-swarm/issues/1). It specifies future implementation and acceptance work. Issue #7 adds a basic foreground `agent-team serve` wrapper around the existing HTTP lifecycle; that does not establish the full lifecycle guarantees or acceptance gates below. Configuration/path authority belongs to issue #2, canonical knowledge preparation to issue #3, persistent model reconciliation to issue #5, and overall standalone smoke evidence to issue #8.

## Invocation and ownership

`agent-team serve` runs one foreground process, with one Uvicorn worker and one runtime owner per resolved state directory. Reload, multiprocess workers, daemonization, and an embedded supervisor are unsupported. Optional s6 must invoke this same lifecycle boundary rather than construct another runtime.

The invocation accepts host, port, startup timeout, and shutdown timeout. Explicit CLI values override their `AGENT_TEAM_HOST`, `AGENT_TEAM_PORT`, `AGENT_TEAM_STARTUP_TIMEOUT`, and `AGENT_TEAM_SHUTDOWN_TIMEOUT` environment counterparts; defaults are `localhost`, `8080`, 60 seconds, and 30 seconds. Ports must be integers from 1 through 65535; deadlines must be positive finite numbers. Configuration selection, overrides, role inheritance, and resolved external state/workspace paths follow issue #2. An explicitly selected missing or invalid configuration fails rather than silently falling back. Freeze the effective configuration once; the engine must consume exactly what startup validated.

Before invoking Uvicorn, perform nonmutating configuration, type, URL syntax, host/port, deadline, and external-path safety validation. Endpoint URLs must be supported HTTP(S) URLs with a host. DNS resolution, connectivity, HTTP authentication, and model-catalog inspection belong to leased startup, not syntax validation. Do not create runtime stores, run retention, configure state-directory log files, or acquire a competing independent lease in this preflight.

FastAPI lifespan owns acquisition and teardown of the sole runtime lease. Acquire it without waiting before model-network checks or any session recovery, migration, retention, store construction, or engine construction. Ownership metadata and lock creation are the necessary exception to otherwise nonmutating failed acquisition. A contender fails immediately without replacing owner metadata or touching durable application state. Owner metadata assists diagnosis; the OS lock is authoritative. Never remove or replace the lock to bypass contention.

After acquiring the lease, verify active model endpoints, prepare canonical knowledge through issue #3's leased preparation boundary, recover sessions, apply retention only after successful knowledge preparation, and construct the engine using the prepared shared store. Skip knowledge access and migration when disabled as required by issue #3. Preserve migration journals and recovery material on failure; do not pretend that startup failure rolls back completed migration, recovery, or retention effects.

## Model endpoint gate

Validate principal, manager, and worker, plus curator only when `memory.enabled`, `memory.shared_knowledge`, and `memory.curator_enabled` are all true. An omitted curator entry inherits worker configuration; an explicitly configured curator follows issue #2's effective configuration rules. Follow issue #5: YAML wins over direct model environment variables; missing/null role fields inherit independently from `models.default`, whose absent/null selection is `auto`; curator inherits worker fields. Explicit empty fields are invalid. Environment bootstrap uses unset `LLM_MODEL` as `auto` and requires `LLM_BASE_URL`. After inheritance every active role requires a nonblank endpoint and selection. Literal `auto` is reserved and cannot name a deployment.

Probe `GET <effective-base-url>/models` once per distinct effective endpoint, normalizing only trailing slashes for equality. Follow issue #5's shared discovery policy: `LLM_API_KEY` is inference-only and `AGENT_TEAM_API_TOKEN` is Agent Team API-only; neither is sent to discovery. Use the same bounded discovery deadline/failure policy as control resolution, within the remaining total startup budget. Require successful HTTP status and a JSON object with list-valued `data`; every entry must have a nonempty string `id`, and advertised literal `auto` is invalid. Deduplicate exact IDs before membership and cardinality checks. Do not infer success from a TCP connection or execute a completion during startup.

| Effective selection | Catalog | Result |
| --- | --- | --- |
| Exact explicit ID | ID advertised after deduplication, including catalogs with other IDs | Accept the configured selection. |
| Exact explicit ID | ID absent, including an empty catalog | Fail `model_not_found`. |
| Literal `auto`, including an effective `LLM_MODEL=auto` selection | Exactly one distinct valid ID | Resolve that ID for this runtime. |
| Literal `auto` | No IDs | Fail `model_not_found`. |
| Literal `auto` | Multiple distinct IDs | Fail `ambiguous_model`; require explicit selection. |
| Any selection | Malformed payload, empty IDs, or reserved advertised `auto` | Fail `invalid_model_response`. |
| Any selection | DNS, transport, timeout, HTTP error, or auth denial | Fail `model_unavailable`, unless the total startup deadline has expired. |

Automatic resolution changes only the immutable runtime configuration passed to the engine. Do not write YAML, environment files, or runfiles; issue #5 owns persistence and reconciliation. Explicit models must match exactly; no fuzzy names or implicit replacement with the first catalog entry.

## Startup deadline and observability

Start one monotonic startup clock before preflight. The total budget covers configuration/path checks, lease acquisition, every endpoint probe, canonical preparation, recovery, retention, engine initialization, lifespan completion, and listener binding. Per-request and storage waits must fit the remaining budget; the budget is not restarted per role or phase. No retries may extend it.

Deadline expiry stops startup and produces `startup_timeout`; safely unwind acquired resources before returning. All readiness-critical work must be cancellable or checked at safe phase boundaries. Wrapping synchronous initialization in `asyncio.wait_for`, or abandoning a background initializer thread, does not meet this contract. An uninterruptible OS/filesystem operation prevents a hard real-time wall-clock guarantee; the implementation report must disclose such platform limits. Do not release ownership while an initializer can continue mutating state.

Emit one newline-delimited JSON `serve_ready` event on stdout only after lifespan succeeds and the intended listener is actually bound. Include event, PID, effective host/port, and resolved state directory. Server logs belong on stderr. A bind failure is `listener_error`; no readiness event is emitted, and startup resources are unwound. Binding may be reserved earlier without accepting requests, but publication still requires every startup gate. A signal or expired deadline wins a race with readiness publication.

Emit a JSON `serve_failed` event on stderr with stable `reason`, `phase`, and sanitized `detail`; exit 1 for startup or cleanup failure. Reasons are `config_error`, `path_error`, `model_unavailable`, `model_not_found`, `ambiguous_model`, `invalid_model_response`, `runtime_in_use`, `startup_timeout`, `listener_error`, `runtime_initialization_failed`, and `shutdown_failed`. Phases identify `preflight`, `lease`, `models`, `knowledge`, `recovery`, `retention`, `engine`, `listener`, or `shutdown`. Knowledge preparation retains issue #3's specific subordinate reason in a separate safe field, under `runtime_initialization_failed`; it must not collapse actionable migration failures into an opaque message.

Diagnostics may name the affected role and safe endpoint scheme/host/port/path and offer remediation. Never emit credentials, authorization headers, URL userinfo/query strings, raw endpoint bodies, model prompts, knowledge records, or unsanitized exception text. HTTP/auth failures may report a status code. A failed contender may report safe owner PID/start time without exposing owner tokens.

## Health, readiness, and admission

An authorized `GET /health` returns HTTP 200 with `{"status":"ok"}` whenever the process can handle that HTTP request. It is liveness only. An authorized `GET /ready` returns HTTP 200 with `{"status":"ok","ready":true}` only after startup completes, the lease remains held, the engine and session store exist, required preparation succeeded, and the state directory remains accessible and writable. Otherwise it returns HTTP 503 with `{"status":"not_ready","ready":false,"reason":"<safe reason>"}`. Preserve existing reasons `config_not_loaded`, `engine_not_initialized`, `runtime_not_owned`, `state_dir_not_accessible`, and `state_dir_not_writable`; add `startup_in_progress` and `runtime_stopping` when applicable.

Both probes retain existing optional Bearer authentication. With `AGENT_TEAM_API_TOKEN` configured, missing or invalid credentials return HTTP 401 with `WWW-Authenticate: Bearer` before probe evaluation. Probes never initialize or repair the runtime. Ordinary requests must likewise not resurrect a missing or draining runtime through lazy initialization; reject new work with HTTP 503 while unavailable or stopping.

Readiness is a local lifecycle/ownership check, not a continuously refreshed dependency check. A model outage after successful startup does not by itself change `/ready`; inference requests expose their normal execution errors. A ready result does not guarantee that the next inference succeeds. Uvicorn need not expose probes before startup or after listener shutdown: connection failure during those intervals is expected, not a promised HTTP 503.

## Signals and cleanup

The first SIGINT or SIGTERM, including during startup, marks the runtime stopping immediately, suppresses readiness publication, stops admission, and emits `serve_stopping` on stderr. Stop accepting new requests, bound draining of HTTP handlers, cancel engine roots and model requests, join owned initialization/tasks, reap tracked children, close runtime/store resources, and release the lease only after mutation has quiesced. Clear configuration, engine, stores, lease references, and compatibility caches so no stale state reports ready or can reinitialize the runtime. Cleanup is idempotent.

Only the lease-holding owner may commit managed durable output, including session/knowledge stores and selected workspace project files/artifacts. Children, including detached `start_new_session` processes, may write only generation-specific scratch. Enforce filesystem/capability isolation denying direct durable writes; scratch working directories or environment filtering do not confine arbitrary same-user subprocesses. Do not pass writable durable handles or unguarded commit channels. Parent-mediated commits check live ownership, current generation, and non-stopping state immediately before mutation. A successor rejects buffered old-generation requests and never blindly imports their scratch. Platforms unable to enforce this confinement must refuse uncontained child modes under this serve contract. No arbitrary subprocess durable-write guarantee is claimed without that enforcement.

A separate monotonic shutdown budget begins at the first stop request; it is not the remaining startup budget or a team-task deadline. Exhaustion or cleanup failure triggers forced local cancellation/reaping, emits `serve_failed` with `shutdown_failed`, and exits 1. Never voluntarily release the lease while owned tasks or processes can still mutate state. Force termination and reaping of tracked process groups where possible; parent exit does not terminate detached children. If owner task quiescence cannot be established, terminate the owner and let OS teardown release its lease; the enforced child boundary above prevents continuing durable writes. Do not retry initialization in that process. A second signal forces owner termination and may skip graceful finalization or leave an orphan writing only old-generation scratch; it does not promise all descendants are reaped. Durable recovery tolerates owner interruption, and successors enforce generation rejection before admission.

After clean cleanup emit `serve_stopped` on stderr and exit 130 for SIGINT or 143 for SIGTERM. A clean programmatic stop exits 0. Cleanup failure takes precedence over these clean-stop codes and exits 1. These are deliberate future CLI semantics, not an assertion about current Uvicorn signal behavior. No process-level clean-stop claim is valid until the signal acceptance checks pass.

## Future acceptance gate

The later implementation must provide automated evidence for:

- Invalid CLI deadlines/ports, malformed or explicitly missing config, unsafe paths, and invalid URL syntax fail before Uvicorn and without durable-state mutation.
- A controllable HTTP endpoint covers unavailable/auth-denied endpoints, malformed catalogs, accepted duplicate singleton IDs, rejected reserved advertised `auto`, absent explicit IDs, explicit selections among multiple models, and zero/one/multiple `auto` outcomes. Shared endpoint probes normalize only trailing slashes and never receive inference or API credentials; no completions or persistent model rewrites occur.
- Two real processes targeting one state directory prove exclusive ownership: the contender fails promptly without modifying incumbent metadata/state; a different directory can start independently. A clean stop permits immediate reacquisition.
- Faults and timeout at each leased phase, including canonical migration and listener bind, produce the agreed reason/phase, no ready event, safe cleanup, and preserved recovery evidence. A cancellation-resistant initializer must not continue writing after ownership is relinquished.
- Real listener tests distinguish authenticated liveness/readiness, prevent HTTP-triggered initialization, reject draining admission, and demonstrate the documented post-start model-outage semantics.
- Real process SIGINT/SIGTERM tests during startup and active work prove exit codes, suppressed readiness races, cancelled work, reaped children, cleared state, and lease reuse. Inject cleanup failure and shutdown deadline expiry; verify exit 1 and ownership-safe termination. Cover a TERM-resistant detached `start_new_session` child continuously writing scratch, attempting direct state/store and selected workspace/artifact writes, and sending buffered commits. Under confinement direct durable writes are denied. After shutdown timeout or a second signal, immediate restart proves old-generation requests are rejected, durable outputs cannot be changed by the old child, and the new owner can write safely. Also verify refusal of uncontained child modes on unsupported platforms. Do not claim graceful finalization or all descendants reaped.
- Capture stdout/stderr events and verify event order, actual binding before `serve_ready`, stable fields, and redaction of injected credentials, URL secrets, bodies, and owner tokens.

Record the tested revision, fixture and process-test results, timeout/fault-injection evidence, and platform exclusions. Existing baseline tests are useful evidence for current behavior, not proof of this future contract.

## Baseline gaps and session record

The reviewed baseline has no `serve` CLI command. `app.main` directly calls Uvicorn; lifespan runs synchronous `_initialize_runtime`; `_require_store` can initialize lazily from HTTP handlers; engine and app independently open knowledge stores; readiness checks globals and local paths; and lifespan teardown does not fully clear globals or guarantee lease release if `engine.close` raises. The runtime lease already provides nonblocking OS exclusivity. The engine already resolves `auto` through discovery, caches by trailing-slash-normalized endpoint, and mutates role configuration; its inference key forwarding to discovery and environment/deployment fallbacks must align with issue #5. Children currently start new sessions, so parent exit cannot establish descendant quiescence. These facts motivate this contract and identify implementation gaps without changing runtime code in this planning issue.

Two delegated agents resolved startup ownership and model selection in round 1; signal behavior, cleanup safety, deadline/binding races, post-start readiness, and event/credential hygiene in round 2; and active curator inheritance plus the parent issue's required `auto` behavior in the final reopened frontier. Evidence came from `cli.py`, `app.py`, `config.py`, `engine.py`, `persistence.py`, model discovery, existing readiness/process tests, parent issues #1/#2, and the accepted issue #3 knowledge contract. The first independent review flagged forced parent termination with surviving child writers. A second two-agent grilling session resolved enforced child confinement, generation-guarded commits, and issue #5 alignment. The second independent review reported no actionable flags. The documentation publication checks passed; runtime implementation and acceptance remain future work.

A newly spawned pair regrilled the reviewer's forced-exit concern and the accepted issue #5 contract. They agreed on enforced sole-owner durable commits, generation-isolated child scratch, guarded commit requests, refusal of uncontained subprocess modes, and the second-signal orphan limitation. They aligned inheritance, deduplication, reserved `auto`, endpoint equality, discovery credentials, and bounded startup discovery, and confirmed an empty frontier before recording these revisions.
